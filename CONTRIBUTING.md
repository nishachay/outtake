# Contributing

## The rule

Nothing ships unverified. A track is visible only after `probeYouTube` confirms the
video exists and permits embedding, and it is re-checked on a rolling cycle.

Concretely: **do not edit `scripts/catalog.json` by hand.** It is generated by
`npm run db:export` and is not read at runtime. A hand edit is a bug the next
export silently reverts. Change the database, or run the importer.

## Setup

Node 18+ (developed on 22) and a free Postgres project.

```bash
git clone https://github.com/nishachay/outtake.git
cd outtake
npm install
cp .env.example .env
```

Neon gives you two connection strings for the same database. Set both:

- `DATABASE_URL` — pooled, hostname contains `-pooler`
- `DATABASE_URL_UNPOOLED` — direct, no `-pooler`

```bash
npm run db:push
npm run db:import
npm run dev
```

Generate secrets with:

```bash
openssl rand -base64 32   # AUTH_SECRET
openssl rand -hex 24      # ADMIN_KEY
```

### Why two URLs

The pooled endpoint routes through PgBouncer in transaction mode, which has no
session affinity. Session state — `SET`, temp tables, multi-statement transactions —
does not survive between statements, and migrations fail in ways that never mention
pooling. Migrations use the direct URL; runtime uses the pooled one.

## Verifying changes

```bash
npm run typecheck
npm run build
```

There is no test framework. The thing being tested is a network contract against
YouTube, and a mocked oEmbed asserts only that the mock was called. Write a
throwaway script instead:

```bash
npx tsx --env-file=.env ./check.ts
```

That is how the verdict table in the README was confirmed — real video ids of known
state, checked against live oEmbed. Prefer that to a unit test with fixtures.

## Adding a track

Through the running app:

1. Submit the URL at `/submit`
2. It lands in `pending_submissions`
3. `npm run db:prefilter` auto-rejects dead, duplicate and non-audio results
4. Review survivors in `/admin/review`, then approve or reject

In bulk:

```bash
npm run db:prefilter
npm run db:prefilter:apply
```

Candidates reach the `candidates` table before they reach `songs`, so a bad batch
is a `DELETE` rather than a git revert across thousands of rows.

## Adding an artist

1. Create them in `/admin/artists`
2. Add tracks through the normal flow — never bypass the probe
3. Fill in `tag` (the hero subtitle) and `initials` (avatar fallback)
4. Add a portrait only if you can find a freely licensed one, and record it in
   `scripts/portrait-credits.json`. If you can't, initials render instead. That is
   the intended fallback.

## Pull requests

Branch from `main`. Conventional commits with a scope:

```
fix(probe): correct the 401 verdict
feat(queries): page the songs endpoint
docs: document the pooled/direct split
```

One logical change per commit. `npm run typecheck` must be clean.

Things a reviewer will check:

- **`Date.now()` or `Math.random()` in rendered output.** Vercel bills an ISR write
  unit per changed regeneration and pauses Hobby deployments for 30 days when a
  limit is exceeded. Seed derived values, as `lib/feed.ts` and `lib/vault.ts` do.
- **Calls to `getCatalog()`.** It has been deleted. Use `lib/queries.ts`.
- **A query with no `LIMIT`.** Assume 3,000 tracks and 88 artists.
- **Anything drawn over the player's pixels.** The Required Minimum Functionality
  forbids it.
- **Copy.** Tracks are "outtakes", not "grails". Avoid leak, rare, exclusive,
  authentic.
